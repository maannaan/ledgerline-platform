1. Mission and assessment facts

Source-derived brief: Ledgerline is a fictional B2B SaaS company with one API service and one PostgreSQL database on a single VM. Deployments are manual over SSH using Docker Compose. Secrets are stored in a machine-level .env and code defaults. Tenant identity is trusted from X-Tenant-Id without authorization. There is no monitoring, alerting, tested backup or runbook.

Acme Retail is already live. Seven more customers are scheduled over six months. The platform must become safe for eight clients, and adding a tenant should take hours rather than weeks or require the engineer to be online.

3. Engineering principles

Secure by defaultIdentity establishes tenant context. A client-controlled header is never authority.
Isolation is testedTest read, create, update, delete, search, reports and admin boundaries.
Observable by designEvery request gets correlation ID, tenant context, trace and structured event.
Automate repeatable workProvision, onboard, deploy, backup, restore and rollback are scripted.
Recover safelyBounded retries, idempotency, health checks, rollback and human escalation.
Evidence over claimsOnly mark an item complete after a reproducible test or captured output.

Architecture choices should be proportional

  • Prefer a managed service when it reduces operational load and fits the budget.
  • Do not introduce Kubernetes, Kafka, service mesh or a large microservice decomposition solely to appear enterprise-grade.
  • Keep the application simple enough to finish and explain. A modular FastAPI service is acceptable if boundaries and scaling limits are documented.
  • Make a distinction between implemented, tested locally, deployed, verified in cloud and planned.

Dedicated client nuance: Delta explicitly requires its own database and own encryption key. Evergreen has a restore target. Granite must have data in a different region. These are distinct requirements. Do not claim the dedicated tier meets all three simply because a tenant is marked dedicated.

Tenant model

  • Tenant registry: tenant ID, tier, region, database target/reference, KMS key reference, status, plan limits and onboarding metadata.
  • Authenticated principal maps to permitted tenant IDs and roles. The API derives tenant context from verified credentials, not a caller-supplied header.
  • For shared tenants, every query is tenant-scoped; add PostgreSQL Row-Level Security if it can be implemented and tested correctly.
  • For dedicated tenants, route only through a server-side tenant registry. A client must not be able to select another tenant's database by changing a request field.
  • Audit admin operations with actor, action, target tenant, timestamp, request ID, result and reason. Do not log bearer tokens or sensitive payloads.

7. Task 1 — Build the platform as code

Required by the brief

  1. Provision from an empty cloud account using IaC.
  2. Use the same code for staging and production.
  3. Support one repeatable onboarding action for shared and dedicated tiers.
  4. Show Acme + Brightpath as shared and Delta as dedicated.
  5. Move Acme seed data; describe production cutover with no data loss and under five minutes downtime.

Implementation plan

  • Terraform root modules per environment; reusable modules for network, database, service, IAM, secrets, monitoring and tenant resources.
  • Use separate state per environment with remote state and locking if available; restrict state access because it can contain sensitive infrastructure metadata.
  • Tenant onboarding should validate a tenant manifest, reserve tenant ID, create/assign data store, create key if dedicated, write secret references, configure limits, run migration/health check and register tenant.
  • Make onboarding idempotent: running it twice should not create duplicate tenant records or keys unexpectedly.
  • Tenant lifecycle states: requested → provisioning → validation → active; failed provisioning should leave a visible failed state and support safe retry/cleanup.

Acme migration plan

For a production migration under five minutes, use a rehearsed expand-and-cutover approach. A defensible design is: create target schema; bulk-copy the baseline while the old system serves traffic; use logical replication/CDC or an application dual-write/outbox mechanism to capture changes; validate counts/checksums; pause writes briefly; apply final delta; switch traffic; verify; keep rollback path. The exact method depends on current PostgreSQL version, privileges and data volume. Do not claim CDC/zero data loss was implemented unless it was actually rehearsed.

Authentication design

  • For assessment demo, a simple tenant API-key table can be acceptable if keys are high entropy, stored hashed, revocable, scoped to tenant and role, and compared safely. A managed identity provider/OIDC is preferable for human/admin access.
  • Resolve token → principal → tenant permissions. Do not trust tenant ID sent by the client.
  • Admin identity must be separate from tenant client identity. Require MFA for human production access where supported and disclose actual state in questionnaire.
  • Use role-based authorization for tenant user, tenant admin, platform operator and read-only auditor.

Database isolation

For pooled tenants, enforce tenant scope in every repository query and ideally PostgreSQL Row-Level Security. Set tenant context per transaction using a safe session-local setting; ensure pooled connections reset context on return. Include negative tests. For dedicated tenants, map tenant to a distinct database connection secret on the server side. Do not let caller-supplied values select database names.

Required automated isolation tests

1. Create tenant A and tenant B using independent credentials.
2. Insert a record for A and a record for B.
3. Authenticate as A:
   - list returns only A records
   - direct GET of B record is denied/not found
   - update/delete B record is denied/not found
   - search cannot expose B data
   - report endpoint returns only A scope
4. Attempt to change X-Tenant-Id to B while using A's token.
5. Confirm response remains scoped to A or request is rejected.
6. Authenticate as B and confirm B can access its own record.
7. Verify admin-only routes reject tenant credentials.
8. Verify audit record exists for privileged admin action and denied attempt.

Delta security questionnaire

Write the questionnaire as if sent to Delta's security team. Each answer must be accurate to the current implementation. Use status labels such as Implemented and tested, Implemented but not independently certified, Planned and Not currently supported. Never claim SOC 2/ISO certification, MFA, key rotation, retention, breach-notification SLA or regional restrictions unless verified.

At least three actionable alerts

  1. API availability burn rate: sustained 5xx/failed request ratio above threshold over a meaningful window; include service and tenant scope.
  2. Latency: p95 /records exceeds 300 ms for sustained window, not a single spike.
  3. Database saturation: connection utilization, CPU, storage or replication lag crosses warning/critical threshold.
  4. Optional: backup failure or backup age exceeds policy; queue backlog; repeated deployment rollback.

Error budget policy — one-page document

  • Define the monthly budget from the availability SLO (for 99.9%, 0.1% of eligible time/requests, depending on chosen method).
  • At 50% consumed: review top contributors and prioritize reliability fixes.
  • At 75% consumed: require reliability review for risky releases and increase monitoring.
  • At 100% consumed: pause non-essential feature releases; permit security, compliance and reliability fixes; require owner approval and rollback plan.
  • Document exceptions, customer communication, review cadence and who can authorize release freeze.

  • Use GitHub Actions OIDC rather than long-lived AWS keys.

  • Keep secrets out of job logs; use least-privilege role for each workflow.
  • Set deployment health checks, minimum healthy capacity and deployment circuit breaker/rollback.

Safe schema changes

Use expand-and-contract: add backward-compatible nullable column/table/index first; deploy app code that can read old/new schema; backfill in batches; switch reads/writes; only remove old schema in a later release. Avoid destructive migration in the same release that first depends on the new schema. For PostgreSQL, consider concurrent index creation and lock/statement timeouts.

Rollback

Application rollback should restore the prior immutable image. Database changes must remain backward-compatible so app rollback is possible. Never assume a destructive schema rollback is safe. Include one command or workflow dispatch that re-deploys the last known-good image and verify it with health and smoke tests.

11. Task 5 — Backups, load and noisy-neighbour isolation

Backup and restore

  • Automated scheduled backups and point-in-time recovery where available; define retention and encryption.
  • Evergreen target: restore within 1 hour and no more than 15 minutes data loss. The assessment requires a restore into a fresh instance and timed evidence.
  • Measure actual RTO (restore duration) and RPO (latest recoverable point relative to incident time). Do not infer RPO from backup frequency alone.
  • Restore into an isolated fresh database, validate schema, row counts, sample records and application connectivity; record start/end and recovery point.
  • Runbook must identify who can authorize restore, how to avoid overwriting production, how to switch connection and how to verify.

Load test

Use the supplied k6 script and update authentication headers to match the implemented design. Target: 200 requests/second for 10 minutes across three tenants; 95% of /records requests under 300 ms. Run only after budget approval and capacity guardrails. Capture actual k6 summary, service metrics, DB metrics and test configuration.

Cobalt noisy-neighbour test

  • Run baseline traffic across Acme, Brightpath and Delta.
  • Run heavy report workload for Cobalt concurrently.
  • Compare other tenants' p95/p99 latency and error rate before/after.
  • Possible mitigations: separate reporting pool/read replica, query timeout, concurrency limit, per-tenant rate limits, queue, resource isolation or dedicated workload class.
  • Do not claim noisy-neighbour isolation if only the report endpoint was mocked or not actually exercised.

12. Task 6 — Run it and lead it

Runbook 1: Onboard a tenant

  1. Receive approved tenant metadata and tier/region requirements.
  2. Validate unique tenant ID, region, data tier, retention and plan limits.
  3. Run onboarding command in the selected environment.
  4. Create isolated database/schema and key/secret references according to tier.
  5. Run schema migration and connectivity checks.
  6. Create tenant credentials through secure channel; store only hashed API key material where applicable.
  7. Run cross-tenant negative tests and smoke tests.
  8. Activate tenant; record owner, date, configuration and audit event.
  9. Send endpoint/test credential through approved secure method; never commit it.

Runbook 2: Restore a database

  1. Declare incident and identify tenant/database/region.
  2. Confirm restore point and obtain required approval.
  3. Restore to a new isolated database; never overwrite source initially.
  4. Record restore start, completion and recovery point.
  5. Validate database integrity, migrations, row counts and application health.
  6. Perform controlled connection switch or tenant routing update.
  7. Monitor errors/latency; keep original database for rollback/forensics.
  8. Document RTO/RPO achieved and notify stakeholders.

Runbook 3: Incident response

  1. Detect and acknowledge alert; assign incident lead and severity.
  2. Identify blast radius: service, environment, tenants, data/security impact.
  3. Preserve evidence and correlate request/trace/deployment IDs.
  4. Mitigate safely: rollback, scale within cap, disable faulty path, isolate tenant or fail over.
  5. Verify recovery with user-facing and infrastructure signals.
  6. Communicate status and next update time.
  7. Capture timeline, cause, contributing factors and follow-up actions.

Post-incident review

Blameless format: summary; customer impact; detection; timeline; root cause; contributing factors; what went well; what did not; remediation actions with owner and due date; prevention/verification. Avoid blaming an individual or writing speculative root causes as facts.

Cost model

Estimate shared and dedicated monthly cost with explicit assumptions and units: compute, database, storage, backup, network egress, logs/metrics, KMS, load balancer and support overhead. Separate fixed platform cost from marginal tenant cost. Use actual calculator/export data or clearly labeled estimates. Include a low/expected/high scenario and cost drivers.

13. Add-on — Reliability Autopilot (safe self-healing)

Differentiator · Only after core acceptance criteria

Proposed candidate-led enhancement, not an explicit requirement in the assessment. It should be a small, bounded remediation controller that observes known signals, evaluates deterministic policies, executes approved actions and verifies recovery. It is not an unrestricted autonomous agent.

Minimum implementation design

  • Use native controls first: ECS health replacement, deployment circuit breaker, autoscaling, RDS automated backups and CloudWatch alarms.
  • For custom remediation, create a small event handler/Lambda or workflow with an explicit allowlist of actions.
  • Policy includes: trigger threshold and duration, eligible environment, eligible service, max attempts, cooldown, maximum capacity, tenant blast radius, approval requirement and verification condition.
  • Idempotency key prevents duplicate actions. Store remediation events and outcomes in an append-only audit log.
  • Dry-run mode must show the proposed action without executing it.
  • Kill switch disables custom remediation globally. Manual override is documented.
  • Never let an LLM decide or execute high-impact production actions. If AI-assisted diagnosis is added later, it may summarize evidence and recommend an action; deterministic policy and human approval control execution.

Demo script

  1. Show normal service health and Autopilot dry-run status.
  2. Trigger a safe staging-only fault, such as a failing deployment health check.
  3. Show detection, policy decision and rollback event.
  4. Show post-action health verification and audit record.
  5. Show that a prohibited action is blocked and requires approval.
Positioning: Present this as “Reliability Autopilot — a small policy-driven remediation layer.” Explain that you deliberately chose deterministic controls over an autonomous LLM because customer data, database integrity and financial workloads require bounded and auditable actions.

9. AI assistance is permitted by the assessment. Add a truthful README section
   describing AI use. I must understand and be able to modify every component.
10. Before any destructive action, explain impact and ask for approval.

WORKING METHOD
- First produce an inventory and a gap analysis mapped to Tasks 1–6.
- Identify all deliberate and incidental flaws in the reference app.
- Propose a small, cost-aware architecture and record assumptions.
- Break work into short phases with acceptance tests.
- Implement one phase at a time. After each phase: run tests, show exact
  results, update STATUS.md and evidence, then ask me to approve the next phase.
- Keep the default branch runnable.
- Use small, meaningful commits. Do not push secrets or force-push.
- Maintain docs/decisions/ ADRs for important trade-offs.
- Keep a known-gaps list. Do not hide unfinished work.

REQUIRED DELIVERABLES
Task 1: Terraform/IaC, staging and production, shared/dedicated tenant
onboarding, Acme/Brightpath shared, Delta dedicated, Acme migration plan and
seed-data demonstration.
Task 2: SECURITY.md, real authentication, server-derived tenant identity,
tenant isolation tests in CI, secret manager, least privilege, encryption,
admin audit trail, honest Delta questionnaire.
Task 3: tenant-aware metrics/logs/traces, filterable dashboard, availability
and latency SLOs, at least 3 actionable alerts, error-budget policy.
Task 4: CI tests + dependency/container scan + isolation test, safe deployment,
one-step rollback, expand/contract schema changes, tenant canary rollout.
Task 5: automated backups, fresh-instance restore evidence with RTO/RPO,

before/after, bottleneck write-up.
Task 6: onboarding, restore and incident runbooks; blameless PIR; shared and
dedicated monthly cost model; <=2 page 90-day plan.

ARCHITECTURE GUIDANCE
AWS is a proposed default only if the approved budget supports it. Consider
VPC, private app/database networking, ALB, ECS Fargate, PostgreSQL/RDS,
Secrets Manager, KMS, CloudWatch/OpenTelemetry, ECR and GitHub Actions OIDC.
Keep Terraform modules reusable across staging and production. Make tenant
routing server-side. For shared tier enforce tenant scope and consider
PostgreSQL RLS; for dedicated tier use a separate database and dedicated key
as actually required. Granite's region isolation is a separate stretch goal
unless time permits.

SECURITY REQUIREMENTS
Never trust X-Tenant-Id as authorization. Derive tenant from authenticated
principal. Fix SQL injection, unscoped record access, insecure admin auth,
secret logging, default credentials, missing transactions/connection
management and container hardening. Add negative tests for read/update/delete,
search and reports across tenants. Avoid logging payloads or credentials.

OBSERVABILITY REQUIREMENTS
Use structured logs with request_id, trace_id, service, env, route, status,
duration and safe tenant context. Avoid high-cardinality metrics. Add traces
for request, auth, tenant resolution and DB calls. Propose SLOs; clearly label
targets as proposed until sufficient measurement exists. Alert only on
sustained actionable conditions.

RELIABILITY AUTOPILOT ADD-ON
Only after all core assessment tasks are in a credible state, implement a
small policy-driven self-healing extension. Prefer native ECS health
replacement, deployment circuit breaker rollback, bounded autoscaling and
backup retry. Custom actions must be allowlisted, idempotent, rate-limited,
cooldown-protected, audited, reversible where possible and verified after
execution. Include dry-run and kill switch. Risky/destructive actions require
human approval. Do not allow an LLM to autonomously execute production
changes. This add-on must not displace core requirements.

18. Live incident drill preparation

The exact incident is not disclosed in advance. Practice a consistent method rather than memorizing one fix.

  1. Clarify impact: Which service/environment/tenants? When did it start? What changed? Is data/security affected?
  2. Establish incident role: Narrate what you are checking and why. Keep a timeline.
  3. Check golden signals: traffic, errors, latency, saturation; compare per-tenant and global views.
  4. Correlate: request ID, trace ID, deployment version, database metrics, queue/backlog, infrastructure events.
  5. Form a hypothesis: State evidence supporting and refuting it. Avoid random restarts.
  6. Mitigate safely: rollback, scale within limit, throttle noisy tenant, disable a faulty non-critical path or fail over only if rehearsed.
  7. Verify: SLO indicators recover, affected tenant confirms, no data integrity regression.
  8. Close the loop: communicate impact, preserve evidence, write follow-up action.

Commands to know (adapt to actual deployment)

# ECS service and task status
aws ecs describe-services --cluster <cluster> --services <service>
aws ecs list-tasks --cluster <cluster> --service-name <service>

# Recent service logs
aws logs tail <log-group> --since 15m --follow

# Recent ECS service events
aws ecs describe-services --cluster <cluster> --services <service> \
  --query 'services[0].events[:10]'

# Terraform inspection — do not apply blindly
terraform fmt -check -recursive

# Local API smoke checks
curl -fsS https://<endpoint>/health

Do not run destructive database, IAM, KMS or networking commands during the drill without confirming target, impact and rollback. Explain the command before executing it.

How to describe incomplete work

Use: “Implemented and tested locally; not deployed to cloud due to the confirmed assessment budget/time constraint.” Or: “Designed and documented; not implemented. The remaining risk is X; next step is Y.” This is stronger than implying the requirement is complete.

Final operating instruction

Build the required platform first. Prove security and recovery. Make it observable. Automate delivery and onboarding. Only then add Reliability Autopilot.

The best submission is not the one with the most components. It is the one a future engineer can deploy, operate, troubleshoot and trust—with clear evidence and no unsupported claims.

Before the Saturday review, you should be able to answer for every major component: What does it do? Why is it there? What can fail? How do we detect that? How do we recover? What did we actually test?
